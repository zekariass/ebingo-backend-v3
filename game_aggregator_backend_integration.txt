The Provider's Workflow looks as follows:
1. The Platform's Backend generates a token, which will be used for user authentication, and inserts it into the game's URL.
2. The Platform's Frontend opens an iframe with the URL obtained from the Platform's Backend.
3. The Provider's Frontend sends information received from the URL to the Provider's Backend.
4. The Provider's Backend sends a request to the Platform's Backend for player data to check authentication and obtain additional player information (e.g., balance).

5. After receiving a response from the Platform's Backend, the Provider's Backend provides the response to the Provider's Frontend.
6. Upon a player's bet, the Provider's Backend sends a request to the Platform's Backend for fund deduction. Upon a successful response, the bet is placed.
7. Upon game completion, the Provider's Backend sends a request to credit the winnings to the Platform's Backend (losses are sent as zero winnings, i.e., the request is sent even in case of a loss).

2. Interaction Scheme
2.1 Introduction

All interactions with the Platform Backend are performed via POST webhooks sent from the Provider to the URL specified by the Platform.

Webhook requests are triggered by the following events:

Session Initialization (init)

Bet – Player balance deduction (bet)

Payout – Credit based on game results (withdraw)

Cancellation – Refund of player funds (rollback)

2.2 Request Handling

The request timeout is 10 seconds.

If the Platform Backend does not respond within this time frame, the request is considered incomplete, and compensatory actions will be taken (see Error Handling section).

The expected HTTP status code for a successful webhook response is 200.

Any HTTP status code other than 200 will be treated as an error, even if the response body contains a status field marked as OK.

Idempotency

Processing of withdraw and rollback webhooks must be idempotent.
The key to idempotency is the data.transactionId field.
This means that when receiving a withdraw or rollback webhook with a data.transactionId that has already beensuccessfully processed before, it should not be processed again, and the response to the request should contain theresponse received during the previous processing.

2.2 Request Signature
The request will have a header called X-REQUEST-SIGN, which contains the signature of the request body in itsoriginal form.
The signature is generated using the algorithm, where the message is the request body in its originalform, and the key is the signature key provided by the Provider upon connection.
The 'signature' header is provided for backward compatibility with the previous signaturealgorithm that was used previously

Request body
{"action":"init","token":"AuthToken","data":{"currency":"USD","operator":"OperatorId","gameMode":"GameMode"}}
Secret key:
7A2DB2F4FE86998735835F538826B262E834662EA297AB8B4286DBFE315A2467521D791A94E3D12A942427A29F

Digest algorithm: SHA256
X-REQUEST-SIGN: 407c4890d288f37fbd7ced0ce73857e77596dcfd4457a296d95ab99d5a97b6b7

2.3 Error Handling
If the Platform's web server cannot process the request, it should respond with an error code. The expected format is:
{
"code": "(Required) For example: INVALID_TOKEN",
"message": "(Optional) Gaming message to display to the player (for debit request)"
}

2.5 Handling Failures
2.51 Mechanism for Compensating Failed Bet Attempts

If the response to the 'bet' webhook results in a TEMPORARY_ERROR or UNKNOWN_ERROR code (or in case of
network failures), the bet will be considered unsuccessful. The Provider's server will automatically trigger a 'rollback'
webhook for this bet.

2.52 Resend Mechanism

This mechanism only operates for the withdraw and rollback webhooks.
If the Operator's Server is inaccessible or if the error code is TEMPORARY_ERROR , the Provider's server will
attempt to resend the withdraw and rollback webhooks gradually, increasing the interval between each resend
attempt (up to 3 days).
The interval increases between each attempt based on the Exponential Backoff strategy.
Exponential Backoff Settings:

{
  "FACTOR": 2,
  "MAX_ATTEMPTS": 50,
  "INTERVAL_MS": 5000,
  "MAX_INTERVAL_MS": 10800000
}

3. Request Structure
All fiat values are rounded to 2 decimal places.
All crypto values are rounded to 9 decimal places.

3.1 Session Initialization

Incoming request:
{
  "action": "init",
  "token": "AuthToken",
  "data": {
    "currency": "USD",
    "operator": "OperatorId",
    "gameMode": "GameMode"
  }
}

Expected response:
{
  "code": "OK",
  "userId": "1",
  "nickname": "user",
  "balance": "100.50",
  "currency": "USD",
  "operator": "OperatorId",
  "userAvatar": "(optional) https://example.com/avatar.png",
  "token": "(optional) game session token (SessionToken)"
}

If a game session token (SessionToken) was not provided, then bet/withdraw/rollback requests will use AuthToken as
the SessionToken.

3.2 Placing a bet from a player's balance
The request is sent at the start of the game. The amount specified in the request body (amount) should be debited
from the player's account or frozen for the duration of the game (until the finalizing request is received) and then
deducted.

Incoming request:
{
  "action": "bet",
  "token": "SessionToken",
  "gameMode": "crash",
  "data": {
    "amount": "100.00",
    "currency": "USD",
    "operator": "OperatorId",
    "user_id": "1",
    "transactionId": "22166608-be33-438a-82d4-844c3b788d2e",
    "gameId": "b1a9dcdb-09f9-44bf-b23d-a5c6019222bc"
  }
}

Expected response:
{
  "code": "OK",
  "balance": "100.00",
  "hideFromStat": true // (optional) indicates whether the player should be hidden from statistics
}

3.3 Crediting the player's balance
The request is sent when the player wins/loses the game. The amount specified in the request (result) should be
credited to the player, the initial bet (amount) is already included in this amount and should not be credited additionally.
If the game supports the creation of multiple bets within one player's game, then the request with the isFinished flag
set to true will indicate that this is the last transaction and the player's game is considered completed.

Incoming request:
{
  "action": "withdraw",
  "token": "SessionToken",
  "gameMode": "crash",
  "data": {
    "user_id": "1",
    "currency": "USD",
    "operator": "OperatorId",
    "amount": "100.02",
    "result": "200.04",
    "coefficient": "2.00",
    "transactionId": "34b40212-7081-427e-9196-1b94a7c0514b",
    "debitId": "ddcd55cd-b5cb-48dc-84de-c37769b56cbb",
    "gameId": "b1a9dcdb-09f9-44bf-b23d-a5c6019222bc",
    "isFinished": true
  }
}

Expected response:
{
  "code": "OK",
  "balance": "100.00"
}

3.4 Refunding the player's balance
The request is sent if the player has not finished the game within 6 hours or if a failure occurs. The amount is equal to
the player's bet and must be credited to the player, or this amount must be unfrozen.
If the game supports the creation of multiple bets within a single player's game, then a request with the isFinished flag
set to true will indicate that this is the last transaction and the player's game is considered finished.

Incoming request:
{
  "action": "rollback",
  "token": "SessionToken",
  "gameMode": "crash",
  "data": {
    "user_id": "1",
    "currency": "USD",
    "operator": "OperatorId",
    "amount": "100.50",
    "transactionId": "34b40212-7081-427e-9196-1b94a7c0514b",
    "debitId": "ddcd55cd-b5cb-48dc-84de-c37769b56cbb",
    "gameId": "b1a9dcdb-09f9-44bf-b23d-a5c6019222bc",
    "isFinished": true
  }
}

Expected response:
{
  "code": "OK",
  "balance": "100"
}
